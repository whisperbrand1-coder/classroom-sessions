THE SIX

Common web application risks 🌐

🕸️

Cross-Site Scripting

Unsafe input runs as code in someone else's browser.

🔓

Broken authentication

Logging in as someone you are not.

🎫

Weak session management

Security misconfiguration

Defaults left on, doors left open.

🔌

🎯 Three of these six appear in your final project — XSS, broken authentication, and weak session management. They appear together, as one chain.
XSS

Cross-Site Scripting 🕸️

XSS happens when a website allows unsafe user input to run as code inside another user's browser. You type it — they run it.

📥

Where it gets in

Comments · forms · search fields · URLs. Anywhere the site takes text from a user and shows it to another user.

💥

What it can do

Steal sessions · post fake messages · redirect users · change what the page says.

Protection

✅ Validate input✅ Encode output ✅ Strip dangerous content✅ Secure coding practices
🔑 Remember the order in the project: the XSS is not the goal. It is how the attacker gets the session cookie. XSS is step one of three.
WHO ARE YOU?

Authentication and session risks 🔑

Authentication verifies that users are who they claim to be. These are the ways it fails:

Weak passwords
Missing MFA
Unlimited login attempts
Sessions that stay active far too long
Stolen or reused session tokens
🎫 The one that catches everybody: weak session management can let an attacker into an account without ever entering the password. They do not need your password if they have your token.
LEAKS & DEFAULTS

Sensitive data exposure and misconfiguration ⚙️

📤

Sensitive data may leak through

Browser storage · source code · unencrypted network traffic · log files · unsafe mobile storage.

⚙️

Misconfiguration looks like

Default passwords · open admin pages · missing updates · detailed error messages · excessive app permissions.

🔍 Detailed error messages are the sneaky one. A helpful stack trace tells an attacker your framework, your version, and sometimes your database structure — for free.

FROM PAPER TO PRACTICE

Framework requirements are high-level 📋

A framework says “protect access to systems”. That sentence protects nothing on its own. Organizations must turn it into:

📜 Policies📝 Procedures⚙️ Technical controls 🧑 Employee actions🗃️ Audit evidence 
Requirement  →  Policy  →  Control  →  Evidence
🗃️ Evidence is the step people forget. If you cannot show an auditor the proof, the control effectively does not exist — no matter how well it works.
RECAP · PART 3 📜

Policies, audits, and the gap between them

POLICY

What a security policy defines 📜

What must be protected
Who is responsible
Which controls are required
How compliance is monitored
What happens when the rules are broken
📌 Example: an Access Control Policy requires MFA for administrator accounts. That single sentence is a requirement, a control and an audit test all at once.

Three types

🏛️

Program policy

The organization's overall security goals.

📄

Issue-specific

One topic — passwords, remote access, data protection.

🖥️

System-specific

Rules for one system — firewall rules, for example.

AUDIT

Internal vs external audits 🔎

A security audit checks whether controls exist and work correctly.

🏠

Internal audit

Performed for the organization · finds weaknesses · supports improvement.

🌍

External audit

Performed by an independent third party · confirms compliance · supports certification and customer trust.

🤝 Internal audits improve you from the inside. External audits give regulators, customers and partners a reason to believe you.
THE BIG ONE

Compliance is not the same as security ⚖️

📋

Compliance

Meets defined requirements · uses policies, controls and evidence · checked at a point in time, during an audit.

🛡️

Security

Protects against real threats · must work continuously · changes as risks evolve.

🔑 Key message: passing an audit does not guarantee security.
An audit is a photograph. An attacker is a video.

THE GAPS

Where organizations fall through 🕳️

📉

Risk assessments not updated

Yesterday's risk list against today's attacker.

📜

Policies become outdated

Written for systems that no longer exist.

🎓

Training incomplete

The human firewall was never actually built.

🗃️

Evidence missing or disorganized

You did the work but cannot prove it.

💥 Impact: these gaps cause audit failures and create real security weaknesses — both at once.

Compliance is the floor, not the ceiling

🧱

Compliance gives you

Minimum requirements · defined controls and responsibilities · evidence for audits.

🚀

Real security also needs

Continuous monitoring · rapid patching · access reviews · control testing · incident-response exercises.

🔑 Compliance is the starting point, not the final goal.

What should the user actually do? ✋

🚫

Do not

Click suspicious links · open unexpected attachments · reply with sensitive information · share passwords or MFA codes.

✅

Do

Report to the security team or teacher · verify through an official website or trusted contact · delete or quarantine after reporting.

🔑 The one-line answer: do not interact with the message. Report it, and verify the request through a channel you chose yourself.
